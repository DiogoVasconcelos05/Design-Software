# ADR-005: Leitura de Dados entre Módulos através de Interfaces de Consulta Só de Leitura

* **Status:** Aceite
* **Data:** 2026-11-01
* **Autor:** Rodrigo Santos

## Contexto
Alguns módulos precisam de ler dados que pertencem a outros. `municipal_reporting` lê viagens de `trip_management` e estações de `station_inventory` para o relatório mensal por freguesia e CO₂ evitado (US-4). `redistribution_planning` lê a ocupação de `station_inventory` para sugerir rotas às carrinhas.

A vista de módulos (`03-particionamento-e-vistas.md`) permite estas dependências e marca `municipal_reporting` como rad-only. Há ainda duas restrições:
* A ADR-001 escolhe um monólito modular por domínio em que cada módulo concentra os seus modelos e contratos, e `common` tem de se manter pequeno.
* O percurso de cada viagem é dado pessoal (RGPD). O relatório só precisa de dados agregados, por isso não deve ter acesso a quem viajou nem por onde.

A leitura mais fácil seria aceder às tabelas ou às entidades de outro módulo, o que cria acoplamento ao esquema de dados e só se descobre quando alguém altera uma coluna.

## Decisão
1. A persistência de cada módulo é privada. As classes de acesso a dados ficam no subpacote `persistence` do módulo e só são usadas por classes desse mesmo módulo. Evitar SQL com JOIN entre tabelas de módulos diferentes.
2. Um módulo que precisa de dados de outro usa uma interface de consulta publicada pelo módulo dono.
3. Interfaces para o relatório municipal:
   * `TripUsageQuery` em `trip_management.query`, que devolve `TripUsageRecord` para um período (estação de origem e de destino, tipo de bicicleta, início, fim e distância). Não inclui identificação do utilizador nem o percurso.
   * `StationLocationQuery` em `station_inventory.query`, que devolve a freguesia de cada estação.
   * `municipal_reporting` junta e agrega os dois resultados em memória.
   * O mesmo padrão aplica-se a `redistribution_planning`**, que lê a ocupação através de `StationOccupancyQuery` em `station_inventory.query`.
4. As interfaces de consulta são implementadas pelo módulo dono, e o consumidor depende só da interface e dos `record`s.

## Verificação
Fitness functions a correr no mesmo comando das restantes:
* Classes em `..persistence..` só são acedidas por classes do mesmo módulo.
* `municipal_reporting` e `redistribution_planning` só dependem de outros módulos de domínio através de pacotes `..query..`.
* Os pacotes `..query..` só contêm interfaces e `record`s.
* Teste unitário: `TripUsageRecord` não tem campos de utilizador nem de percurso.

## Consequências
* **Positivas:**
  * "Só leitura" passa a ser verificável por ferramenta, e não só uma intenção escrita.
  * Os módulos donos podem mudar o esquema de dados sem partir os leitores, desde que mantenham a interface.
  * O relatório fica sem acesso a dados pessoais, o que reduz a exposição ao RGPD.
  * Mantém `common` pequeno..
* **Negativas:**
  * Mais interfaces e `record`s para manter, e cada novo tipo de relatório pode exigir uma nova consulta.
  * A agregação em memória de um mês de viagens pode ser pesada. As consultas são por período e paginadas, e o relatório é um processamento mensal.
  * A leitura usa a mesma base de dados das operações. O relatório deve correr fora das horas de ponta.

## Alternativas Rejeitadas
* `municipal_reporting` lê diretamente as tabelas ou entidades de outros módulos: rejeitada porque acopla o relatório ao esquema interno, obriga a JOIN entre domínios e dá acesso a dados pessoais desnecessários.
* Colocar as interfaces e os `record`s de leitura em `common`: rejeitada porque faria `common` crescer e tornaria o pacote um ponto de acoplamento global.
* Projeção própria do relatório alimentada por eventos: rejeitada por agora. Acrescenta infraestrutura e consistência eventual, que não compensam num relatório mensal e com 3 semanas de prazo. Fica como caminho de evolução se o volume crescer.
* Chamar o serviço completo de `trip_management`: rejeitada porque expõe operações de escrita e a garantia de "só leitura" ficaria apenas por convenção.
